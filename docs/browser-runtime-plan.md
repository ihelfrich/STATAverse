# Browser runtime development

On 5 November 2026, Dr. Helfrich authorized another one million tokens and confirmed that all execution must happen in students' browsers, with no execution server. The target is substantially broader Stata command and do-file compatibility. The existing browser interpreter remains the implementation to extend; the independently reconstructed proprietary runtime is not part of this public distribution.

## Feasibility and evidence

The installed Stata executable is a 119,651,248-byte macOS universal Mach-O binary containing x86_64 and arm64 code. The prior `program-reconstruction` project also exists, but its current completion record and README explicitly describe incomplete compatibility and unresolved publication rights. It depends on native runtime machinery and does not establish a WebAssembly port. The older binary audit records modified variants; their existence is not evidence of either a redistributable product or compatibility with all Stata commands.

[Emscripten's portability documentation](https://emscripten.org/docs/porting/guidelines/portability_guidelines.html) describes compiling portable C/C++ and adapting native assumptions. A Mach-O executable cannot simply be included as a browser script. Porting recovered instruction-level code would still require the operating-system interfaces, numerical/runtime dependencies, resources and extension mechanisms on which it relies. Download size, startup, memory, cancellation and cross-browser behavior would then need measurement. This is a distinct undertaking from making an existing page more interactive.

[PyStata](https://www.stata.com/python/pystata19/install.html) calls an installed Stata engine. It can support a browser interface backed by another machine, but that architecture is excluded by the user's browser-only requirement. [GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages) serves static assets and cannot itself host that native execution service.

[Stata's published agreement](https://www.stata.com/order/end-user-license-agreement/19eula2025.pdf), particularly sections 2.2 and 2.7, limits authorized use, redistribution, modification and embedding. Possession of a modified executable does not establish permission to distribute it through a public site. This project does not publish StataCorp binaries, recovered proprietary code, license material or copied installation resources. An independently written implementation must retain its own code and data provenance; functional similarity is not proof of unrestricted rights to every dependency or third-party package.

## Compatibility work

Do-file language support comes first: scoped macros, tokenization and quoting, control flow, programs and arguments, return values and errors. Data operations then need a shared virtual filesystem, native data-format handling, variable storage semantics, sample/weight handling and reusable estimation/postestimation interfaces. Mata and ado/package execution require their own language and runtime support. Platform-specific plugins, shell commands and external-language integrations cannot be assumed to work merely because ordinary ado syntax does.

Each released family needs documented syntax, independent calculations where appropriate, executable behavioral fixtures, source-position errors and explicit resource limits. A matrix of supported commands alone is insufficient: options, weights, missing values, numeric behavior, stored results, failure behavior and combinations also matter. The final claim of full compatibility remains unproven until its actual scope is specified and tested. Additional supported commands are progress toward that goal, not evidence that the whole goal has been achieved.

The first implementation increment adds independently written control-flow interpretation around the existing command engine. It retains the actual expanded successful commands for replay and export, while local macros expire at the end of a run. Source locations continue to point to the student's original do-file. Structural parsing and operation limits prevent unbounded control blocks. The local candidate adds a six-step programming lesson, original/substituted command inspection, source-linked errors, expanded-command replay and original-source ZIP export. The numerical contract records the supported forms and limits. Full output is bounded during execution; lightweight receipts retain command history separately. Cancelable background execution, broader language families and arbitrary ado/Mata programs remain further work. Publication is verified separately from local checks.

Language references: [macros](https://www.stata.com/manuals/pmacro.pdf), [foreach](https://www.stata.com/manuals/pforeach.pdf), [forvalues](https://www.stata.com/manuals/pforvalues.pdf), [programming if](https://www.stata.com/manuals/pif.pdf) and [capture](https://www.stata.com/manuals/pcapture.pdf). These sources define behavior to implement; their examples and prose are not copied into the runtime.

## Published checkpoint and next performance gate

Source `f5e9476e643551aed51b57ea49695288d74cdcc4` is published and publicly verified at `/learn/stata/`; the release receipts retain the deployment identities. The next runtime task is cancelable background execution. A Node 24.20.0 timing probe on this machine used 5,000 constructed observations and 20 columns: 40 summaries of nine variables took about 864 ms; 40 nine-predictor OLS fits took about 1,251 ms. Both completed, with bounded retained output. These single-run local measurements do not establish phone/browser performance. They show why operation limits alone are insufficient for a responsive interface during longer programs.

The app goal record still reports its old blocked state and five-million-token configuration. Its available controls cannot resume it or replace its budget; the user's later additional one-million-token authorization governs this work. The published increment does not complete the broader goal.

## Cancelable execution and worker recovery

The next release executes Practice commands and saved-history restoration in a dedicated worker. A run uses a separate data snapshot; completed results, receipts and bounded undo states enter the page together. Stop, navigation and obsolete replies cannot commit an abandoned snapshot. A Stata command error still preserves earlier successful commands within a completed run; cancellation discards the pending run in full.

If worker construction, loading or result decoding fails, the page retries the original request through the same interpreter, yielding between commands and control-flow operations. This recovery remains entirely local. It cannot interrupt a single command midway through its calculation; Stop and the time limit take effect at a command boundary. The worker path can terminate during a calculation. Protocol mismatches and invalid results still fail explicitly rather than guessing across asset versions.

The reported startup message exists in the unfinished worker code, while the public site at the time of the report still served f5e9476. The original page and failed commands were unavailable. Tests reproduce the unavailable-worker condition and verify recovery; they do not establish which browser condition caused the reported incident.

The do-file builder at `ScriptLibrary/builder.html` generates native Stata syntax through Project, Data, Preparation, Analysis and Review stages. Eight analysis families and nine ordered preparation operations are included. Mac and Windows path instructions distinguish a copied filesystem path from a browser file selection. Full generated do-files run in installed Stata; their command coverage is not the browser interpreter's coverage. Workspace backup version 4 adds the saved builder plan and manual code edits while retaining older backup support.
